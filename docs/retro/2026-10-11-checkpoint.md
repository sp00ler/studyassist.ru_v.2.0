## Что исправлено в коде

1. Support poller передавал updates без секрета в защищённый webhook, получал 403 и всё равно подтверждал offset. Добавлен `/api/telegram/support`, отдельный SUPPORT-секрет, ожидание записи в БД, повтор при сбое и стабильный ID сообщения для дедупликации.
2. Исправлена гонка курсора ChatWidget: подтверждение собственного сообщения больше не пропускает более ранний ответ оператора.
3. Уведомления заказов и счетов ожидаются независимо по каналам; админский интерфейс показывает ошибки вместо безусловного обещания отправки.
4. Админская заявка требует email и сохраняет контакты в полях заказа. Публичная форма сохраняет выбранные контакты и для авторизованного клиента.
5. `package-lock.json` был исключён из Git. Из-за этого на VPS оставался старый lock без resvg, а `npm ci` падал. Исключение удалено, согласованный lock добавлен в репозиторий.
6. В PR #24 все три пути создания счёта атомарно создают `Payment` и обновляют `Order`, затем отправляют уведомления. До исправления админские счета сохраняли только `Order.paymentId`, а webhook искал `Payment.yukassaId` и сообщал `unknown payment`. Telegram теперь также показывает результат отправок и использует контакт заказа.

## Открытый дефект: зависание получения updates

Факты из логов VPS (время приведено как в логе, не пересчитывать молча в Томск):

- 10.10 в 04:52:59 два update получили HTTP 200.
- До 08:35:34 были `ETIMEDOUT`, `ECONNRESET`, `EFATAL: AggregateError`.
- Затем до перезапуска не было новых строк, хотя пользователь отвечал в специально созданной группе от имени владельца.
- После `pm2 restart studyassist-support-poll` в 17:34:25 обработаны updates `319870383`–`319870386`, все с HTTP 200; ответ появился на сайте.

Вывод: перезапуск восстановил получение накопленных updates. Подозрение на зависший сетевой запрос/polling loop; точный механизм ещё не доказан. Не объявлять сетевые ошибки из старых строк текущим отказом и не считать PM2 online доказательством работы цикла.

Следующий инженерный шаг:
